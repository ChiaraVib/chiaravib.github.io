0. Inputs

1. Toy ECC scheme on secp256k1

Curve: y² = x³ + 7 over Fp, p = 2²⁵⁶ − 2³² − 977, with base point G of prime order n. The scheme is an ECIES/ElGamal-style hybrid construction (assumed to match Part 1 of Homework 1):

  1. Key generation: private key d, deliberately restricted to [1, 2¹⁶ − 1]; public key Q = d·G.
  2. Encryption: pick a random ephemeral scalar k; send C₁ = k·G; compute the shared point S = k·Q; derive a keystream KS = SHA-256(S.x ‖ counter) and output C₂ = M ⊕ KS.
  3. Decryption: recompute S = d·C₁ = d·k·G = k·Q and recover M = C₂ ⊕ KS.

Role of the keys: d is secret and is the only thing that lets the receiver recompute S; Q is public and lets anyone encrypt; k is a one-time ephemeral secret that randomizes every encryption (same message, different ciphertext). Security rests on the Computational Diffie–Hellman problem (CDH): given Q = d·G and C₁ = k·G, compute S = d·k·G. CDH is at most as hard as the Elliptic Curve Discrete Logarithm Problem (ECDLP: given Q and G, find d), so a hard ECDLP is necessary but not sufficient. The hash step also assumes SHA-256 behaves like a pseudorandom function.

3. Comparison of the two schemes

Caesar cipherToy ECC scheme

Main similarity: both hide the plaintext behind a single secret value (a shift, a scalar) and both are broken once the key space is small enough to enumerate. Main difference: Caesar is a fixed substitution, so the ciphertext keeps the plaintext letter statistics and is attackable by frequency analysis whatever the key; the toy ECC scheme is not designed to expose such statistics, and its weakness here is the tiny private-key range (plus the design issues in Section 5).

4. Statistical cryptanalysis of the Caesar cipher

Idea: a shift of k rotates the letter histogram. English statistics are estimated from a training corpus. All three methods below try every candidate shift s = 0…25, i.e. an exhaustive search over a key space of only 26 keys. They differ only in the score used to pick the best candidate, because exhaustive search alone cannot tell which of the 26 outputs is the correct one:

  • Letter frequencies (χ²): minimise Σ (Oj − Ej)² / Ej, with Ej = N·P(j).
  • Bigram scoring: maximise Σ log P(xixi+1) with a Laplace-smoothed bigram model.
  • Trigram (crib) counting: decrypt with each of the 26 keys and count frequent trigrams (THE, AND, ING, ION, …).

5. Attacking the toy ECC scheme

Because 1 ≤ d < 2¹⁶, the attacker only needs the d with d·G = Q, where Q is public. Two attacks on the key pair from Section 1:

  1. Exhaustive search: compute G, 2G, 3G, … until the point equals Q: O(N) group operations.
  2. Baby-step giant-step (BSGS): with m = ⌈√N⌉, store j·G for 0 ≤ j < m (j = 0 is the point at infinity), then test Q − i·m·G for i = 0, 1, …; a match with j·G gives d = i·m + j. Cost O(√N) time and memory.

Statistical attack vs. key-space attack

Both attacks are, at bottom, a search over the key space: 26 candidates for Caesar, 2¹⁶ − 1 for the toy ECC. The difference is how a candidate is checked. Against ECC the attacker has a perfect verifier, the public key: a candidate d is correct if and only if d·G = Q, without looking at the ciphertext at all. Against Caesar there is no such check, because every shift produces some string of letters, so the attacker needs a statistical score to decide which candidate looks like English. This works because the ciphertext is a deterministic, frequency-preserving image of the plaintext. The ECC keystream is meant to be pseudorandom (a design goal, not proved here), so language-frequency analysis is not an appropriate tool there, and it is not needed either. As a consequence, the Caesar attack can return a wrong key on short texts, while an ECC match is exact.

Why this fails against a properly configured ECC scheme

With a private key spread over ≈ 2²⁵⁶ values, even the best generic algorithms (BSGS, Pollard rho) need ≈ 2¹²⁸ group operations, and BSGS also 2¹²⁸ stored points; the √N attack above is practical only because N = 2¹⁶. No structure is known that speeds up the secp256k1 ECDLP.

Optional: other weaknesses

From the restricted key space: brute force, BSGS, Pollard's kangaroo (interval ECDLP, little memory). From the toy design: no integrity protection (C₂ is malleable), a repeated or weak ephemeral k (leaks plaintext XORs or the shared secret), and no check that C₁ lies on the curve; these would remain with a full-size key.
